# Bancada do NF-002 — 2026-09-23 — **não é o aceite**

Primeira execução da bancada `scripts/medir-nf002.mjs`, feita para provar que a
bancada funciona. **Isto não aprova o NF-002**, e o registro de aceite
(`nf-002-envio-pedido-AAAA-MM-DD.md`) continua em branco.

Três motivos, e nenhum deles é detalhe:

1. **Não foi no tablet.** Rodou de um Node na mesma máquina do servidor. O
   aparelho que o cliente usa tem outro processador, outro rádio e outra pilha
   de rede, e é ele que o requisito mede. O tablet ainda não existe (A12).
2. **Não foi no Wi-Fi do salão.** Foi em `127.0.0.1`: zero rede. O NF-002 é o
   requisito que mais sente a rede, e o número daqui não diz nada sobre ela.
3. **Falta o outro número.** O NF-002 são dois: a resposta do servidor e o
   feedback visual de 100 ms, que só se mede filmando a tela a 60 fps. Este
   registro cobre um.

## O que rodou

| Campo | Valor |
|---|---|
| Comando | `npm run medir:nf002` |
| Servidor | build de produção (`next start`), local, porta 3100 |
| Banco | Supabase local em Docker, massa do `seed.sql` recém-criada |
| Loja e mesa | Jardim Secreto, mesa 9, tablet de teste "Bancada NF-002" |
| Produto | Bolinho de mandioca (sem complemento obrigatório) |
| Execuções | 20, cada uma com `Idempotency-Key` nova |

## O resultado

| Número | Valor |
|---|---|
| p95 da resposta de `POST /api/orders` | **40 ms** |
| Máximo | 109 ms |
| Pedidos com id distinto | 20 de 20 |
| Veredito do script | `PASSOU` (limite: p95 < 500 ms) |

Os 20 pedidos foram criados no banco local e morreram no `db reset` seguinte.
Em staging ou no salão, a equipe precisa cancelá-los, e o registro de aceite tem
campo para dizer quem cancelou.

## O que este número serve para dizer

Que o servidor e o banco cabem com folga no orçamento de 500 ms quando a rede
não conta: sobram 460 ms para o Wi-Fi do salão e para o rádio do tablet. Se a
medição no aparelho reprovar, o culpado não é a consulta ao banco.
